## 作業手順(詳細)

### 手順1: バックアップ対象と世代管理の設計

まず「何を」「どこに」「何世代」残すかを決めます。世代管理とは、バックアップを1つだけ上書き保存するのではなく、複数世代を保持しておくことで、数日前・数週間前の状態にも戻せるようにする考え方です。

| 項目 | 設計例 |
|---|---|
| バックアップ対象 | `/var/www/html`(Webコンテンツ)、`/etc`(設定ファイル) |
| バックアップ先 | `/backup`(可能であれば本番用ディスクとは別の場所) |
| 取得頻度 | 毎日1回(深夜など負荷の低い時間帯) |
| 世代数 | 直近7世代(1週間分)を保持 |

世代数は「壊れたことに気づくまでの期間」を目安に決めます。すぐ気づけるなら世代数は少なくてよく、気づくのが遅い運用ならより多く残す必要があります。

### 手順2: 手動でtarコマンドによるバックアップを試す

まずは自動化する前に、手動でアーカイブ作成を確認します。

```bash
# バックアップ保存先ディレクトリを作成
sudo mkdir -p /backup

# 以降はsudoなしでバックアップスクリプトを実行できるよう、所有者を自分自身に変更しておく
sudo chown "$(whoami):$(whoami)" /backup

# /etc ディレクトリを日付付きでアーカイブ化(c:作成 z:gzip圧縮 v:詳細表示 f:ファイル名指定)
sudo tar czvf /backup/etc-$(date +%Y%m%d).tar.gz /etc
```

`date +%Y%m%d` はその日の日付(例:20260830)を出力するコマンドで、ファイル名に埋め込むことで世代ごとに別ファイルとして残せます。`/etc` の中には一般ユーザーでは読み取れないファイルも含まれるため、読み取り側の権限として `sudo` を付けています(書き込み先の `/backup` はすでに自分の所有になっているので、この後作るスクリプトでは `sudo` なしで書き込めます)。

実行すると `tar: Removing leading '/' from member names` という警告が表示されることがありますが、これはtarが絶対パスの先頭の `/` を取り除いて格納する仕様によるものなので、エラーではありません。

> ここで作成した `etc-*.tar.gz` は動作確認用のファイルです。次の手順で自動化するのはWebコンテンツ(`/var/www/html`)のバックアップで、世代管理の対象も `backup_*.tar.gz` という命名のファイルに限定します。確認が終わったら `rm /backup/etc-*.tar.gz` などで削除しておくと、後で紛らわしくなりません。

### 手順3: バックアップシェルスクリプトの作成

毎回手打ちするのではなく、スクリプト化して自動化の土台を作ります。以下では保存先を `/home/user/scripts/backup.sh` とします。`user` の部分は実際のログインユーザー名に置き換えてください(`whoami` コマンドで確認できます)。

```bash
mkdir -p ~/scripts
nano ~/scripts/backup.sh
```

エディタが開いたら、以下の内容を貼り付けて保存します(`nano` の場合は `Ctrl+O` → `Enter` で保存、`Ctrl+X` で終了します)。

```bash
#!/bin/bash
# backup.sh : Webコンテンツを日付付きでバックアップし、古い世代を削除するスクリプト

# バックアップ対象
SRC_DIR="/var/www/html"
# バックアップ保存先
BACKUP_DIR="/backup"
# 日付(秒まで含めて重複を防ぐ)
DATE=$(date +%Y%m%d_%H%M%S)
# 残す世代数
KEEP_GENERATIONS=7

# 保存先がなければ作成
mkdir -p "$BACKUP_DIR"

# アーカイブ作成(詳細表示のvは付けない。毎日実行するログが肥大化するのを防ぐため)
tar czf "${BACKUP_DIR}/backup_${DATE}.tar.gz" "$SRC_DIR"

# アーカイブ作成に失敗した場合はここで処理を止める
if [ $? -ne 0 ]; then
    echo "$(date): バックアップの作成に失敗しました" >&2
    exit 1
fi

# 古い世代の削除(新しい順に並べて、KEEP_GENERATIONS件より後ろを削除)
cd "$BACKUP_DIR" || exit 1
ls -1t backup_*.tar.gz | tail -n +$((KEEP_GENERATIONS + 1)) | xargs -r rm -f
```

- `ls -1t` は更新日時が新しい順に1行1ファイルで表示します。
- `tail -n +N` はN行目以降だけを表示するので、「新しい7件より後ろ」だけを取り出せます。
- `xargs -r rm -f` は該当ファイルがある場合だけ削除を実行します(該当なしでもエラーになりません)。
- アーカイブ作成の直後に終了コード(`$?`。直前に実行したコマンドの結果を表す値で、`0`なら成功)を確認しています。ここでチェックせず世代削除まで進んでしまうと、ディスク容量不足などで今回のバックアップが失敗した場合でも過去の世代が削除されてしまい、有効なバックアップが1つも残らないという最悪の事態になりかねません。

保存したら実行権限を付与します。

```bash
chmod +x ~/scripts/backup.sh
```

一度手動で実行し、正しくアーカイブが作られるか確認しておきましょう。

```bash
~/scripts/backup.sh
ls -l /backup
```

### 手順4: crontabの書式を理解する

`cron` は「分 時 日 月 曜日」の5つの欄で実行タイミングを指定します。

| 欄 | 意味 | 指定範囲 |
|---|---|---|
| 分 | 0〜59分 | 0-59 |
| 時 | 0〜23時 | 0-23 |
| 日 | 日付 | 1-31 |
| 月 | 月 | 1-12 |
| 曜日 | 曜日(0が日曜) | 0-6 |

`*` はすべての値を意味します。例えば「毎日午前2時0分」に実行したい場合は次のように書きます。

```text
0 2 * * *
```

### 手順5: crontabにジョブを登録する

初めて `crontab -e` を実行すると、使用するテキストエディタの選択を求められることがあります。迷ったときは `nano` を選ぶと操作がシンプルでおすすめです。

```bash
crontab -e
```

エディタが開くので、末尾に以下の1行を追加します。標準出力・標準エラー出力の両方をログファイルへ残すのがポイントです(cronの実行環境はPATHなどが最小限しか設定されないため、コマンドやスクリプトは省略せずフルパス〈絶対パス〉で書きます。`crontab` の中では `~` は展開されないので注意してください。`user` の部分は実際のログインユーザー名に置き換えます)。

```text
0 2 * * * /home/user/scripts/backup.sh >> /var/log/backup.log 2>&1
```

保存してエディタを終了すると登録が完了します。登録後は必ず一覧表示で確認しましょう。

```bash
crontab -l
```

> **注意:** `crontab -r` は登録されているジョブを確認なしにすべて削除してしまうコマンドです。`-e`(編集)や `-l`(一覧表示)と打ち間違えないよう気をつけましょう。

> **ヒント:** このままだと動作確認のために深夜2時まで、場合によっては丸1日待つことになります。今すぐ動きを確認したいときは、一時的にスケジュールを `* * * * *`(毎分実行)に書き換えて数分待ち、`/var/log/backup.log` や `/backup` 配下にファイルが増えることを確認してから、本来の `0 2 * * *` に戻す、という方法がおすすめです。

### 手順6: ログの確認方法を理解する

この案件の冒頭でも触れた `journalctl` を使って、cronの実行状況を含めたシステム全体のログを確認してみましょう。

```bash
# cron関連のログを確認(Debian系はcron、RHEL系はcrondというサービス名で登録されています。お使いの環境に無い方は「ユニットが見つかりません」と表示されますが問題ありません)
journalctl -u cron
journalctl -u crond

# 直近1時間のログだけ表示
journalctl --since "1 hour ago"
```

従来型のテキストログは `/var/log` 配下にあります。

```bash
# Debian系(直近50行を表示)
tail -n 50 /var/log/syslog

# RHEL系(直近50行を表示)
tail -n 50 /var/log/messages

# 自作したバックアップログ(直近50行を表示)
tail -n 50 /var/log/backup.log
```

### 手順7: logrotateの概念を理解する

バックアップログ(`/var/log/backup.log`)も、放置すると際限なく肥大化してしまいます。`logrotate` はログファイルを一定サイズ・一定周期で切り分け、圧縮・削除して世代管理してくれる仕組みです。設定ファイルは `/etc/logrotate.d/` 配下に1ファイルずつ置きます。

以下の内容で `/etc/logrotate.d/backup-sample` というファイルを作成してみましょう。

```text
/var/log/backup.log {
    weekly
    rotate 4
    compress
    missingok
    notifempty
}
```

- `weekly`:週1回のタイミングでローテーション(ログファイルの切り替え)を行う
- `rotate 4`:過去4世代分まで残す
- `compress`:ローテーションした古いログを圧縮する
- `missingok`:対象のログファイルが存在しなくてもエラーにしない
- `notifempty`:ログの中身が空ならローテーションしない

設定した内容は、次のコマンドで強制的に実行して動作確認ができます(本番反映前のテストとして有効です)。

```bash
sudo logrotate -f /etc/logrotate.d/backup-sample
```

### 手順8: 最重要工程 ― リストアテストを実施する

バックアップは「取ること」がゴールではありません。実際に元へ戻せることを確認して、初めて意味を持ちます。ここが今回の案件でいちばん大切な工程です。

```bash
# 保存されているバックアップを新しい順に確認
ls -lt /backup/backup_*.tar.gz

# テスト用の一時ディレクトリを用意
mkdir -p /tmp/restore_test

# 最新のバックアップファイルを取得して展開する(x:展開 z:gzip解凍 v:詳細表示 f:ファイル名指定)
LATEST_BACKUP=$(ls -t /backup/backup_*.tar.gz | head -n 1)
tar xzvf "$LATEST_BACKUP" -C /tmp/restore_test

# 中身が想定通りか確認
ls -la /tmp/restore_test/var/www/html

# 元データとの差分がないか比較(-r:サブディレクトリも含めて再帰的に比較)
diff -r /tmp/restore_test/var/www/html /var/www/html
```

手順2で触れたとおり、`tar` は絶対パスを渡してアーカイブを作成すると、先頭の `/` を取り除いた形でパスをそのまま保存します。そのため展開すると `/tmp/restore_test/var/www/html` のように、元のディレクトリ構造がフルパスのまま再現されます。

`diff -r` で差分が出力されなければ、バックアップと現状のデータが一致していることになります(バックアップ取得後に本番側が更新されていれば差分が出るのは正常です)。確認が終わったら、テスト用ディレクトリは削除しておきましょう。

```bash
rm -rf /tmp/restore_test
```

定期的に、この手順を実際に行う習慣をつけましょう。

## よくあるエラーと対処法

| 症状 | 主な原因 | 対処法 |
|---|---|---|
| cronジョブが実行されない | crontabの書式ミス(欄の数がずれている、スペースの入れ忘れ) | `crontab -l` で書式を再確認。分・時・日・月・曜日の5欄になっているかを1つずつ数える |
| cron経由だとコマンドが失敗する | cronの実行環境はPATHが最小限で、対話シェルと異なる | スクリプトやコマンドを絶対パス(フルパス)で記述する。必要な環境変数はスクリプト内で明示的に設定する |
| 手動実行では成功するのに、cron経由だと権限エラー(Permission deniedなど)になる | バックアップ先ディレクトリの所有者がrootのままだったり(手動実行は`sudo`で気づきにくい)、対象ディレクトリの読み取り権限が実行ユーザーに無い | `ls -ld /backup` で所有者・権限を確認し、`sudo chown` で実行ユーザーの所有に変更する。読み取り対象側の権限もあわせて確認する |
| バックアップ先の容量不足でエラー | 世代管理が機能しておらず古いファイルが溜まり続けている | `df -h` で空き容量を確認。スクリプトの削除処理(世代管理ロジック)が正しく動いているか再確認する |
| バックアップは取れているがいざという時に戻せない | リストア確認を一度も行っていない | 定期的に手順8のリストアテストを実施し、結果を記録に残す運用にする |
| ログに何も出力されず失敗原因が分からない | crontabの行に `>> ログファイル 2>&1` を付け忘れている | リダイレクト設定を追加し、標準出力・標準エラー出力の両方をログに残す |

## 覚えておきたいポイント(暗記のコツ)

**「バックアップは取って終わりではなく、戻せて初めて完成」**

このフレーズをそのまま覚えてください。どれだけ立派な自動化スクリプトを組んでも、リストアの手順を検証していなければ、本番障害の瞬間に「実は壊れたバックアップだった」と気づくことになりかねません。「取得」と「復元確認」は必ずセットで運用する、という意識を持ちましょう。

### あわせて覚えておきたい語呂合わせ

- **cronの5つの欄の順番**:「分・時・日・月・曜日」です。頭文字をつなげて「ふん・じ・にち・げつ・よう」と声に出して覚えると、欄の数(5個)や順番を間違えにくくなります。
- **tarのオプション**:バックアップ作成は `czvf`(Create・gZip・Verbose・File)、リストア(展開)は `xzvf`(eXtract・gZip・Verbose・File)。「作るときはc、戻すときはx」で対になっていると覚えましょう。
- **3-2-1ルール**:本格的な運用でよく使われる指針で、「3つ以上のコピーを、2種類以上の媒体に、うち1つは離れた場所(オフサイト)に」保存するという考え方です。今回学んだ世代管理はこの土台にあたり、発展課題の「オフサイトバックアップ」につながっていきます。

## 振り返り・発展課題

今回はローカルディスクへの `tar` によるフルバックアップ(対象データ全体を毎回まるごと取得する方式)を扱いました。実務ではさらに次のような発展があります。

- [ ] `gpg` などによるバックアップデータの暗号化
- [ ] cronジョブが失敗した場合にSlackやメールへ通知を飛ばす仕組みの追加
- [ ] Zabbixなどの監視ツールと連携し、バックアップの成否やディスク容量を継続的に監視する体制づくり

まずは今回の「フルバックアップ+世代管理+リストア確認」という基本形を確実に押さえることが、これら発展課題への土台になります。
