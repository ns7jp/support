# 案件06: Webサーバー構築案件(Nginx)

## 案件カテゴリ

Webサーバー構築・運用(インフラ構築系)

## この案件で身につくスキル

- [ ] Nginx(エンジンエックス。世界的に広く利用されているWebサーバー用ソフトウェア)のインストールと基本設定
- [ ] systemctl(Linuxでサービス〈常駐して動き続けるプログラム〉の起動・停止・状態確認を行うコマンド)によるサービス管理
- [ ] ufw(Uncomplicated Firewall。Linuxの簡易ファイアウォール〈不正な通信を遮断する仕組み〉管理ツール)によるポート開放
- [ ] ドキュメントルート(Webサーバーが公開するファイルを置くディレクトリ)へのファイル配置と権限の考え方
- [ ] curl・ブラウザを使った疎通確認(そつうかくにん。サーバーとクライアント端末の間できちんと通信できるかを確かめること)の方法
- [ ] Nginxのログファイル(アクセスログ・エラーログ)の基礎的な読み方
- [ ] `nginx -t` による設定ファイルの文法チェックという、現場で必須のトラブルシュート手順

## 想定シナリオ(依頼内容)

あなたはインフラ担当として、社内の開発チームからこんな依頼を受けました。

> 「新しく用意してもらったLinuxサーバー(案件05で構築したサーバー)の上に、検証用のWebページを公開できる環境がほしいです。まずは簡単なHTMLページが表示できればOKなので、Nginxを入れてWebサーバーとして動かしてください。社内の他の端末からブラウザでアクセスできる状態にしてほしいです。」

このように「とりあえず動くものを見せてほしい」という依頼は現場で非常によくあります。難しい機能は不要で、①インストール→②起動→③公開→④疎通確認、という一連の流れを迷わず実行できることが評価されます。焦らず一つずつ進めれば必ずできる内容なので、安心して取り組んでください。

## 事前準備・必要な環境

- [ ] 案件05で構築したLinuxサーバー(Ubuntuまたは同系統のディストリビューション〈Linuxをすぐ使える形にまとめて配布したもの〉を想定)
- [ ] サーバーにSSH(Secure Shell。ネットワーク経由でサーバーを安全に遠隔操作するための仕組み)接続できるクライアント端末
- [ ] サーバー上で管理者権限(sudo)が使えるユーザー
- [ ] サーバーとクライアント端末が同じネットワーク内にあり、疎通できること
- [ ] 事前にパッケージリストを最新化していること(`sudo apt update`)

| 項目 | 内容 |
|---|---|
| OS | Ubuntu Server(LTS版を推奨) |
| ソフトウェア | Nginx(ディストリビューションの標準リポジトリから導入) |
| 開放するポート | 80番(HTTP) |
| 確認方法 | ブラウザ、または`curl`コマンド |

## 作業目的(ゴール)

- サーバーにNginxをインストールし、サービスとして常時稼働させる
- ドキュメントルートに簡単なHTMLファイルを配置し、社内向けの検証ページとして表示できるようにする
- ファイアウォールで80番ポートを正しく開放し、外部端末からアクセスできる状態にする
- ログファイルを見て、アクセスがきちんと記録されていることを確認できるようになる

## 作業手順(詳細)

### 手順1: パッケージ情報の更新とNginxのインストール

まずパッケージリストを最新化してから、Nginxをインストールします。

```bash
sudo apt update
sudo apt install nginx -y
```

インストールが終わったらバージョンを確認しておきましょう。

```bash
nginx -v
```

### 手順2: サービスの起動と自動起動設定

Nginxはインストール直後に自動で起動していることが多いですが、念のため明示的に起動・有効化しておきます。

```bash
sudo systemctl start nginx
sudo systemctl enable nginx
sudo systemctl status nginx
```

`status`コマンドを実行して、`active (running)`と表示されていればサービスは正常に稼働しています。`enable`をしておくことで、サーバー再起動後も自動的にNginxが立ち上がるようになります。

> **ヒント**: 慣れてきたら `sudo systemctl enable --now nginx` のように、有効化と起動を1つのコマンドでまとめて行うこともできます。仕組みを理解するまでは、上記のように分けて実行するのがおすすめです。

### 手順3: ドキュメントルートへのHTMLファイル配置

Nginxのデフォルトのドキュメントルートは`/var/www/html`です。ここにあるファイルがWebページとして公開されます。まずは既存の初期ページをバックアップしてから、自分で作った簡単なHTMLファイルを配置してみましょう。

```bash
sudo cp /var/www/html/index.html /var/www/html/index.html.bak
sudo nano /var/www/html/index.html
```

エディタで以下のような簡単な内容に書き換えます。

```html
<!DOCTYPE html>
<html lang="ja">
<head>
  <meta charset="UTF-8">
  <title>検証用ページ</title>
</head>
<body>
  <h1>社内検証用サーバーです</h1>
  <p>Nginxで公開しています。</p>
</body>
</html>
```

保存したら、所有者と権限が適切かも確認しておきます。一般的にはNginxのプロセスを動かしているユーザー`www-data`(Debian/Ubuntu系でWebサーバーなどが標準で使う専用ユーザー)が読み取れる状態であればOKです。

```bash
ls -l /var/www/html/index.html
```

### 手順4: ufwでの80番ポート開放

デフォルトではファイアウォールがHTTP通信をブロックしている場合があります。Nginxをインストールすると、ufw用の「アプリケーションプロファイル」(あらかじめ用意された、特定のソフト向けのポート設定のひな形)が自動登録されるので、それを使って開放するのが簡単です。

```bash
sudo ufw allow 'Nginx HTTP'
```

プロファイル名を使わずポート番号で直接指定する方法もあります。

```bash
sudo ufw allow 80/tcp
```

設定後は必ず反映状況を確認します。

```bash
sudo ufw status
```

`80/tcp`が`ALLOW`になっていれば成功です。まだufw自体を有効化していない場合は`sudo ufw enable`が必要ですが、案件05で有効化済みであればこの手順は不要です。

### 手順5: 動作確認(curl・ブラウザ)

サーバー自身から確認する場合は、以下のようにローカルホスト(自分自身を指すアドレス)へ`curl`します。

```bash
curl http://localhost
```

用意したHTMLの内容が表示されれば、サーバー内部では正しく動いています。HTTPステータスコード(通信結果を表す3桁の番号)だけを手早く見たいときは、`-I`オプションでヘッダー情報のみ取得すると便利です。

```bash
curl -I http://localhost
```

`HTTP/1.1 200 OK`のように`200`が返ってくれば正常です。

次に、社内の別端末のブラウザからサーバーのIPアドレスにアクセスし、同じ内容が表示されることを確認します(例:`http://サーバーのIPアドレス/`のようにアクセスします)。サーバー自身のIPアドレスが分からない場合は、以下のコマンドで確認できます。

> 補足: `docs/02_environment-setup.md`の案内どおり「ホストオンリーアダプタ + NATアダプタ」の構成でVMを作っている場合、この「別端末」はホストPC自身(ホストPCのブラウザからVMのIPアドレスへアクセスする)として体験できます。ホストPC以外の本物の別端末からアクセスしたい場合は、ネットワークアダプタをブリッジアダプタに切り替える必要がある点も覚えておきましょう。

```bash
ip a
```

または、より簡潔に表示したい場合は次のコマンドも使えます。

```bash
hostname -I
```

### 手順6: ログファイルの確認

Nginxはアクセスがあるたびに、以下の2つのログファイルに記録を残します。

| ログファイル | 内容 |
|---|---|
| `/var/log/nginx/access.log` | 誰が・いつ・どのページにアクセスしたかの記録 |
| `/var/log/nginx/error.log` | 設定ミスや処理中に発生したエラーの記録 |

`access.log`の典型的な1行は、次のような形式になっています。

```
サーバーへのアクセス元IPアドレス - - [30/Aug/2026:10:15:32 +0900] "GET / HTTP/1.1" 200 612 "-" "アクセスしたブラウザのUser-Agent情報"
```

| 部分 | 意味 |
|---|---|
| アクセス元IPアドレス | どの端末からアクセスされたか |
| `[30/Aug/2026:10:15:32 +0900]` | アクセスがあった日時 |
| `"GET / HTTP/1.1"` | リクエストの内容(メソッド・パス・HTTPバージョン) |
| `200` | HTTPステータスコード(200は正常、404は未検出、500はサーバー内部エラーなどを表す) |
| `612` | サーバーがクライアントへ送信したデータ量(バイト数) |

最初からすべてを覚える必要はありません。まずは「ステータスコードの数字」と「どのパスにアクセスされたか」の2点を読み取れれば、初心者のうちは十分です。

最新の記録をリアルタイムで見るには`tail`コマンドに`-f`(follow=追跡の意味で、ログに新しい行が追記されるたびに自動で表示を更新するオプション)を付けると便利です。

```bash
sudo tail -f /var/log/nginx/access.log
```

この状態でブラウザからページを再読み込みすると、新しい行がリアルタイムで追加される様子が確認できます。確認が終わったら`Ctrl + C`で監視を終了しましょう。過去の記録だけを確認したい場合は、`-f`を付けずに末尾の行数を指定する方法もあります。

```bash
tail -n 20 /var/log/nginx/access.log
```

## 完了確認チェックリスト

- [ ] `systemctl status nginx`で`active (running)`と表示される
- [ ] `systemctl is-enabled nginx`で`enabled`と表示され、再起動しても自動起動する設定になっている
- [ ] `sudo ufw status`で80番ポート(またはNginx HTTP)が`ALLOW`になっている
- [ ] サーバー自身から`curl http://localhost`で配置したHTMLが表示される
- [ ] 社内の別端末のブラウザから、サーバーのIPアドレス指定でページが表示される
- [ ] `access.log`にアクセスした記録が残っている
- [ ] `sudo nginx -t`で設定ファイルの文法エラーが出ていない

ここまですべてチェックできれば、Webサーバー公開の基本はマスターできています。

## よくあるエラーと対処法

**症状1: ブラウザから接続できない・タイムアウトする**

ほとんどの場合、ファイアウォールでポートを開け忘れていることが原因です。`sudo ufw status`を実行し、80番が許可されているか確認してください。ufw以外にも、クラウド環境の場合はセキュリティグループ側の設定も別途必要になる点に注意しましょう。

**症状2: HTMLファイルを配置しようとすると「Permission denied」と表示される**

`/var/www/html`は管理者権限が必要なディレクトリです。ファイルの編集や上書きには`sudo`を付けて実行してください。エディタ自体を`sudo`なしで開いてしまうと保存時にエラーになるので、`sudo nano ...`のように最初から権限を付けて起動するのがコツです。

**症状3: `systemctl start nginx`が失敗する、または起動後すぐに落ちる**

設定ファイルに文法エラーがある可能性が高いです。まず以下のコマンドで文法チェックを行いましょう。

```bash
sudo nginx -t
```

`syntax is ok`と`test is successful`という趣旨のメッセージが両方表示されればファイルは正常です。エラーが出ている場合は、指摘された行番号を頼りに設定ファイルを見直してください。

**症状4: ページは表示されるが、更新した内容が反映されない**

ブラウザ側のキャッシュ(以前読み込んだ内容を一時的に保存しておく仕組み)が残っている場合があります。スーパーリロード(強制再読み込み)を試すか、`curl`で直接確認して切り分けましょう。

## 覚えておきたいポイント(暗記のコツ)

Nginxのトラブルは、次の三段階の順番で切り分けると迷いません。

| 順番 | 実行すること | 目的 | 覚え方 |
|---|---|---|---|
| ① | `sudo nginx -t` | 設定ファイルの文法にミスがないか調べる | **t**est(検査) |
| ② | `systemctl status nginx` | サービスが実際に動いているか確認する | **s**tatus(健康チェック) |
| ③ | `access.log` / `error.log` を見る | 何が起きているかを記録から読み解く | **l**og(カルテ) |

病院にたとえると、①まず検査(test)で異常の有無を調べ、②次に健康状態(status)を確認し、③最後にカルテ(log)を読んで経過を追う、という流れと同じです。「**t→s→l**」の順番、あるいは「テスト→ステータス→ログ」とそのまま声に出して覚えてしまうのが一番の近道です。

**ミニクイズで定着させましょう**

> Q. ブラウザでページが表示されず、真っ白な画面になってしまいました。最初に打つべきコマンドは何でしょうか?
>
> A. `sudo nginx -t`です。設定ファイルの文法チェックが正常なら、次に`systemctl status nginx`でサービスの稼働状態を確認し、それでも原因が分からなければログを見て絞り込みます。

この切り分け順序はNginxに限らず、Apache(アパッチ。Nginxと並んでよく使われるWebサーバー用ソフト)など他のミドルウェア(OSとアプリケーションの間で働くソフトウェアの総称)のトラブルシュートにも応用できる考え方です。ぜひ他の案件でも同じ順番を意識してみてください。

## 振り返り・発展課題

今回はデフォルトの設定のまま、シンプルなHTMLファイルを表示するところまでを行いました。次のステップとして、以下のような発展課題にも挑戦してみると理解が深まります。

- [ ] ドキュメントルートを`/var/www/html`以外の任意のディレクトリに変更する設定ファイルの書き換え
- [ ] サーバー名(`server_name`)を設定し、複数サイトを1台のサーバーで公開する「バーチャルホスト」の仕組みを試す
- [ ] アクセスログの形式(ログフォーマット)をカスタマイズしてみる
- [ ] SSL/TLS(通信を暗号化する仕組み)を使い、HTTPS化に挑戦する
- [ ] Nginxをリバースプロキシ(裏側のアプリケーションサーバーへ通信を中継する役割)として使う構成を学ぶ
