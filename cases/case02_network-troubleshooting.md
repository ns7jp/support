# 案件02: 社内ネットワーク疎通トラブルの切り分け対応

## 案件カテゴリ

| 項目 | 内容 |
|---|---|
| 分野 | 社内インフラ運用・ヘルプデスク対応 |
| 対応領域 | ネットワーク疎通トラブルの一次切り分け |
| レベル | 初級 |
| 目安時間 | 2〜3時間 |

サーバー構築エンジニアの現場では、サーバーそのものの構築だけでなく「利用者からの問い合わせに対応する」場面が非常に多くあります。今回は、社内ネットワークでよくある「特定の1台だけ繋がらない」というトラブルを題材に、原因を論理的に絞り込む練習をします。

## この案件で身につくスキル

- OSI参照モデル(通信の仕組みを7つの階層に分けて考える基本モデル)の下位層を使った切り分けの考え方
- `ipconfig`(Windowsでネットワーク設定を表示するコマンド)によるIPアドレス設定の確認方法
- `ping`・`tracert`(`traceroute`)・`nslookup`という3大トラブルシュートコマンドの使い方
- APIPA(Automatic Private IP Addressingの略。DHCPサーバーからIPアドレスを取得できなかったときに、OSが自動で割り当てる169.254.x.xのアドレスのこと)などの典型トラブルパターンの理解
- 問い合わせ対応における「近い所から遠い所へ」という切り分けの型
- 非エンジニアの依頼者にも、専門用語をかみ砕いて状況や対処結果を伝える報告力

## 想定シナリオ(依頼内容)

あなたは社内ヘルプデスク担当のサーバー構築エンジニアです。ある日、営業部のAさんから次のような問い合わせが届きました。

> 「さっきまで使えていた共有サーバー(ファイルサーバー)に、急に繋がらなくなりました。隣の席の同僚は問題なく使えているので、私のPCだけおかしいと思います。」

この一報だけを頼りに、電話やチャットでヒアリングをしながら、Aさんのパソコン単体の問題なのか、ネットワーク機器やサーバー側の問題なのかを切り分けていきます。

## 事前準備・必要な環境

| 項目 | 内容 |
|---|---|
| 検証用PC | Windows 10/11、またはLinux(Ubuntu等)のPC 1台 |
| 権限 | 一般ユーザー権限でOK(IP再取得を試す場合のみ管理者権限があると安心) |
| ネットワーク環境 | 自宅や検証用のLAN・Wi-Fiで代用可(社内ネットワークが無くても学習できます) |
| 使用コマンド | `ipconfig`(Windows)/ `ip addr`(Linux)、`ping`、`tracert`/`traceroute`、`nslookup` |

- [ ] コマンドプロンプトまたはPowerShell(Windows)、ターミナル(Linux/Mac)を起動できる
- [ ] 自分のPCがネットワークに接続されている
- [ ] 紙またはメモアプリで、聞き取った内容や実行結果を記録できる準備がある

社内ネットワークが手元にない場合は、自宅のWi-Fiルーター環境を「社内LAN」に見立てて、同じ手順を練習すれば十分に効果があります。

**ヒント**: 手順の中に出てくる「対象サーバー」の代わりとして、同じWi-Fiに接続した別のスマートフォンやPCを使うと、より実践に近い形で練習できます。相手側の端末で`ipconfig`(Windows)や`ip addr`(Linux/Mac)、あるいはスマートフォンのWi-Fi詳細設定を開けば、そのIPアドレスを確認できます。

## 作業目的(ゴール)

「なんとなく繋がらない」という感覚的な報告ではなく、OSI参照モデルの下位層(物理層・データリンク層・ネットワーク層)を意識しながら、**自分のPC → 最寄りのネットワーク機器 → 外部 → 対象サーバー** の順に一つずつ疎通を確認し、根本原因を筋道立てて特定できるようになることがゴールです。あわせて、非エンジニアの依頼者にも分かりやすく状況を説明できる報告力も身につけます。最初は難しく感じるかもしれませんが、確認する順番さえ守れば、誰でも必ず原因の手がかりにたどり着けます。焦らず一つずつ進めていきましょう。

## 作業手順(詳細)

### ステップ0: OSI参照モデルで考える切り分けの土台

通信のトラブルは、下記の下位層から順番に疑うのが基本です。上の層(アプリケーションなど)を疑う前に、まず「物理的に繋がっているか」「住所(IPアドレス)は正しいか」を確認します。

| 層 | 役割(ざっくり) | 確認する内容の例 | この案件で使う主な確認方法 |
|---|---|---|---|
| 物理層 | ケーブルや電波など「モノ」の接続 | LANケーブルの抜け・断線、Wi-Fiの接続状態 | 目視・手触りでの確認 |
| データリンク層 | 同じネットワーク内の機器同士のやり取り | ネットワークアダプタ(PCの通信機能を担う部品)が有効か、リンクランプ(ケーブル接続時に点灯するランプ)が点いているか | デバイスマネージャーやランプの目視確認 |
| ネットワーク層 | 異なるネットワークをまたぐ通信(IPアドレスでの通信) | IPアドレス・サブネットマスク・デフォルトゲートウェイ設定 | `ipconfig`/`ip addr`、`ping`、`tracert`/`traceroute`、`nslookup` |

3つの層は、「モノ(ケーブルや電波)」→「隣(同じネットワーク内の機器)」→「住所(IPアドレス)」の順に確認していくとイメージしやすくなります。この後のステップも、基本的にこの順番(物理層→データリンク層→ネットワーク層)で進めていきます。

### ステップ1: ヒアリングと物理層の確認

まずAさんに「いつから」「有線かWi-Fiか」「他のアプリ(ブラウザなど)は使えるか」を確認します。そのうえで、目視・手触りで「モノ」の接続、つまり物理層をチェックします。

- [ ] LANケーブルがPCとポートの両方にしっかり差さっているか
- [ ] ケーブルに損傷がないか、Wi-Fi接続がオンになっているか
- [ ] タスクトレイのネットワークアイコンに「未接続」や「!」マークが出ていないか

### ステップ2: 自PCのネットワーク設定を確認する(ipconfig)

Windowsでは次のコマンドで、自分のネットワーク設定をまとめて確認できます。

```powershell
ipconfig /all
```

ここで確認したいのは、主に次の4つの値です。

| 項目 | 意味 |
|---|---|
| IPアドレス | ネットワーク上での自分のPCの「住所」にあたる値 |
| サブネットマスク | IPアドレスのうち、どこまでが自分のネットワークの範囲かを示す値 |
| デフォルトゲートウェイ | 自分のネットワークの外(社外など)へ出るときの出入り口となる機器(ルーターなど)のアドレス |
| DNSサーバー | サーバー名などの「名前」をIPアドレスに変換(名前解決)してくれるサーバーのアドレス |

ここで確認した値、特にデフォルトゲートウェイのIPアドレスは、この後のpingの手順で使うのでメモしておきましょう。

Linuxの場合は以下を使います。

```bash
ip addr show
```

ここで最も注目したいのが、IPアドレスの先頭2オクテット(オクテットとは、ピリオド「.」で区切られた各数字のかたまりのことです。IPv4アドレスは8ビットずつ4つに分けて表記されるため、それぞれをオクテットと呼びます)です。もし `169.254.x.x` が表示されていたら要注意です。これは前述のAPIPAで、PCがDHCPサーバー(IPアドレスを自動で配布するサーバー)からアドレスを取得できず、OSが仮のアドレスを自動で割り振った状態を意味します。この場合、原因の多くはDHCPサーバーとの通信不良や、そもそもケーブル・Wi-Fiが繋がっていないことにあります。

### ステップ3: pingで「近い所から遠い所へ」疎通確認する

`ping`(相手先に信号を送って応答があるか確認するコマンド)を使い、次の順番で確認します。順番を守ることが、原因箇所を絞り込む最大のコツです。

**ポイント**: 以下のコード中のIPアドレスはあくまで説明用の例です。実際に試すときは、ステップ2で確認した自分の環境の値(デフォルトゲートウェイのアドレスなど)に読み替えてください。

```powershell
# 1. 自分自身(PC内部のネットワーク機能が動いているか)
ping 127.0.0.1

# 2. デフォルトゲートウェイ(ステップ2で確認した、社内LANの出入口となるルーターなどのアドレス)
ping 192.168.1.1

# 3. 社外(パブリックDNSサーバーなど、インターネット上の有名なIPアドレスに直接ping。名前解決を経由しない疎通確認)
ping <パブリックDNSサーバーのIPアドレス>

# 4. 対象の共有サーバー
ping 192.168.1.20
```

※ `<パブリックDNSサーバーのIPアドレス>` の部分には、検索すればすぐに見つかる、世界的に広く使われているパブリックDNSサービスのIPアドレスを入れてください。本書では固有のIPアドレスの掲載を避けているため、あえてプレースホルダーにしています。

Linuxの場合は回数指定オプションをつけると出力が見やすくなります。

```bash
ping -c 4 192.168.1.1
```

- 1に失敗する → PC自体のネットワーク機能に問題がある可能性(まれ)
- 2に失敗する → 物理層・データリンク層、または自PCのIP設定に問題がある可能性が高い
- 2は成功し3に失敗する → 社内から社外への出口(ルーターやファイアウォール)に問題がある可能性
- 3は成功し4に失敗する → 対象サーバー側、またはサーバーまでの経路に問題がある可能性

> **注意**: 対象サーバーの設定によっては、ping(ICMPという通信方式を使います)への応答が意図的に無効化されている場合があります。この場合、サーバー自体は正常に動作していてもpingだけが失敗することがあるため、4に失敗した場合は「サーバーの管理者にpingの応答設定も確認してもらう」ことも忘れないようにしましょう。

### ステップ4: tracert/tracerouteで経路を確認する

pingだけでは「途中のどこで止まっているか」までは分かりません。そこで経路上の各機器(ルーターなど)を順番に表示する `tracert`(Linuxでは `traceroute`)を使います。

```powershell
tracert 192.168.1.20
```

```bash
traceroute 192.168.1.20
```

※ Linuxで`traceroute`コマンドが見つからない場合は、`sudo apt install traceroute`(Debian/Ubuntu系の場合。他のディストリビューションではパッケージ管理コマンドが異なります)のようにインストールすれば使えるようになります。

応答が途中の機器で止まっている場合、その機器の手前までは通信できているが、その先に問題があると推測できます。

### ステップ5: nslookupでDNS名前解決を確認する

サーバーに名前(例: `fileserver.example.com`)でアクセスする場合、その名前をIPアドレスに変換する**DNS**(名前解決の仕組み)が正しく機能しているかも重要な確認ポイントです。

```powershell
nslookup fileserver.example.com
```

`nslookup`はWindowsだけでなくLinuxやMacでも同じ書式で使えます。もしLinuxでコマンドが見つからない場合は、`dnsutils`(Debian/Ubuntu系)や`bind-utils`(RHEL/CentOS系)といったパッケージをインストールすると使えるようになります。

正しいIPアドレスが返ってくればDNSは正常です。エラーが出たり、想定と異なるIPアドレスが返ってきたりする場合は、DNSサーバーの設定ミスや、DNSサーバー自体の不調が疑われます。

### ステップ6: 原因の特定と対処、報告

ここまでの結果を突き合わせて原因を絞り込み、対処します。代表的な対処例として、APIPAが疑われる場合はDHCPからのIP再取得を試します。

```powershell
ipconfig /release
ipconfig /renew
```

(Linuxでは`sudo dhclient -r`→`sudo dhclient`の実行や、`nmcli`を使った接続の再取得などが同様の操作にあたります。使用しているディストリビューションのネットワーク管理方式に合わせて読み替えてください。)

そのほかの原因パターン(ケーブル不良、IPアドレス重複、DNS設定誤りなど)への対処法は、この後の「よくあるエラーと対処法」を参照してください。

対処後は必ずステップ3・4・5を再実行し、正常化したことを確認してからAさんへ報告します。報告のときは、専門用語をそのまま使うのではなく、次のように分かりやすい言葉に置き換えることを意識しましょう。

> **Aさんへの報告例**
> 「PCがネットワークの住所(IPアドレス)をうまく取得できていない状態でした。設定を取得し直したところ正常に戻り、共有サーバーへの接続も確認できました。もし再発するようでしたら、いつでもご連絡ください。」

## 完了確認チェックリスト

- [ ] `ipconfig /all`(または`ip addr`)でIPアドレスが正常範囲であり、APIPA(169.254.x.x)ではないことを確認した
- [ ] サブネットマスク・デフォルトゲートウェイが、正常に使えている他の端末と整合していることを確認した
- [ ] デフォルトゲートウェイへの`ping`が通ることを確認した
- [ ] 社外への`ping`が通り、社内から外への出口に問題がないことを確認した
- [ ] `nslookup`でサーバー名からIPアドレスへの名前解決ができることを確認した
- [ ] 対象サーバーへの`ping`が通ることを確認した
- [ ] 原因と対処内容、確認結果を記録し、依頼者へ分かりやすく報告した

## よくあるエラーと対処法

| 症状 | 主な原因 | 対処法 |
|---|---|---|
| IPアドレスが169.254.x.xになっている | DHCPサーバーからIPアドレスを取得できていない(APIPA) | ケーブル・Wi-Fi接続を確認し、`ipconfig /release`→`ipconfig /renew`でIP再取得を試みる |
| デフォルトゲートウェイへの`ping`がタイムアウトする | ケーブル不良、Wi-Fi未接続、ネットワークアダプタの無効化など物理層の問題 | ケーブルを挿し直す、別のポート・別のケーブルで試す、無線接続を再接続する |
| 同じIPアドレスを使う機器が社内にあるという警告が出る | IPアドレスの重複(固定IP設定のミスや、DHCP範囲外の手動設定) | 該当PCのIP設定を確認し、DHCPによる自動取得に変更するか、重複しない固定IPに修正する |
| `nslookup`でエラーや想定外のIPが返る | DNSサーバーの設定が誤っている、またはDNSサーバー自体が停止している | `ipconfig /all`でDNSサーバーのアドレス設定を確認し、正しい値に修正する。必要に応じて`ipconfig /flushdns`でDNSキャッシュをクリアし、DNSサーバー側の稼働も確認する |
| `ping`は通るのに共有フォルダにアクセスできない | ネットワーク層より上位(共有設定・権限・ファイアウォールなど)の問題 | ネットワーク疎通自体は正常なので、アクセス権限やファイル共有サービスの設定を別途確認する |

## 覚えておきたいポイント(暗記のコツ)

- **「近い所から遠い所へ」**: 自分 → デフォルトゲートウェイ → 社外 → 目的のサーバー、の順に確認すれば、どこで通信が途切れているかを効率よく絞り込めます。
- **「モノ→隣→住所」で下から確認する**: OSI参照モデルの物理層(モノ:ケーブルや電波)→データリンク層(隣:同じネットワーク内の機器)→ネットワーク層(住所:IPアドレス)の順にチェックすると、見落としが減ります。
- **169.254 = DHCP行き止まりのサイン**: APIPA(Automatic Private IP Addressing)のアドレスです。このアドレスを見たら、まず物理的な接続とDHCPサーバーとの通信を疑う、と反射的に覚えておきましょう。
- **3大コマンドは役割と言葉の由来で覚える**: 下の表のように、コマンド名の由来とセットで覚えると混同しにくくなります。

| コマンド | 何を確認する? | 覚え方 |
|---|---|---|
| `ping` | 相手まで信号が届くか(疎通) | ソナーの「ピン」のように信号を送って反応を確認するイメージ |
| `tracert`/`traceroute` | どこで止まっているか(経路) | trace(たどる)+ route(経路)→経路をたどって確認する |
| `nslookup` | 名前が正しくIPアドレスに変換されるか(名前解決) | name server(ネームサーバー)に lookup(調べる)→名前を調べる |

## 振り返り・発展課題

- 今回はネットワーク層までの確認でしたが、実際にはポートが開いているかを確認する `Test-NetConnection`(PowerShell。指定したIPアドレスやポート番号への接続可否をまとめて調べられるコマンド)や `telnet` を使ったトランスポート層以上の切り分けも重要です。余裕があれば調べてみましょう。
- Wireshark(通信内容を詳細に記録・解析するツール)を使って、実際のパケットの流れを可視化する練習をすると理解がより深まります。
- 今回の手順をもとに、社内向けの「一次切り分けフローチャート」を自分で作成してみると、手順の理解がさらに定着します。
- 固定IPを使う機器が多い環境では、IPアドレス管理台帳を整備しておくと、重複トラブルの予防につながります。

## ポートフォリオへの書き方例

実務経験がなくても、学習した内容を成果物として言語化することで十分にアピールできます。以下のような形でまとめてみましょう。

> **社内ネットワーク疎通トラブルの切り分け対応(学習演習)**
> 「特定の1台のPCのみ社内共有サーバーに接続できない」という想定シナリオに対し、OSI参照モデルの下位層(物理層・データリンク層・ネットワーク層)に基づく切り分け手順を実践。`ipconfig`によるIP設定確認、`ping`による自PC→デフォルトゲートウェイ→社外→対象サーバーの段階的疎通確認、`tracert`による経路確認、`nslookup`によるDNS名前解決確認までを一貫して実施し、APIPA割り当てやDNS設定誤りなど典型的な原因パターンとその対処法を整理した。あわせて、確認結果を専門用語のまま伝えるのではなく、非エンジニアの依頼者にも分かりやすい言葉で報告する練習も行った。

このように「何を」「どんな手順で」「どんな考え方に基づいて」行ったかを書くことで、実務未経験でも論理的な切り分け能力があることを採用担当者に伝えることができます。
