# 案件03: 共有フォルダのアクセス権不具合対応

## 案件カテゴリ

Windows環境のファイルサーバー運用・共有フォルダのアクセス権(パーミッション、コンピュータ上のファイルやフォルダに対して「誰が」「何をしてよいか」を定めるルール)に関するトラブルシューティング案件です。社内ヘルプデスクや情報システム部門で非常に頻度の高い問い合わせ内容であり、サーバー構築エンジニアを目指すうえで必ず押さえておきたい基礎スキルです。

## この案件で身につくスキル

- Windowsの「共有アクセス許可」と「NTFSアクセス許可」という2種類の権限の違いを理解する力
- 2つの権限が競合したときに「実際にはどちらが適用されるか(実効権限)」を判断する力
- 部署単位でグループを設計し、グループ単位で権限を管理する運用の基本
- `net share` や `icacls` といったコマンドラインでの権限確認・変更スキル
- ユーザーからの曖昧な問い合わせ内容を整理し、原因を切り分けるヒアリング力(相手から状況を聞き出し、要点を整理する力)

## 想定シナリオ(依頼内容)

あなたは社内ヘルプデスク担当のエンジニアです。ある日、情報システム部の先輩から次のような依頼が来ました。

> 「経理部のAさんから『営業部の共有フォルダの中身が見えてしまう』と連絡がありました。逆に、営業部のBさんからは『自分の部署の共有フォルダに保存しようとすると書き込みエラーになる』という報告も来ています。ファイルサーバー(仮に `FileServer01` とします)の共有設定を確認して、部署ごとに正しくアクセスできる状態に直してもらえますか?」

このように、**「見えてはいけないものが見えてしまう」「見えるべきものが見えない・書き込めない」**という、権限設定の食い違いから起きる典型的なトラブルです。焦らず1つずつ確認していけば必ず解決できる内容ですので、落ち着いて手順を追っていきましょう。

## 事前準備・必要な環境

| 権限 | 管理者(Administrator)権限を持つアカウント |
| テストデータ | 営業部用フォルダ・経理部用フォルダをそれぞれ用意(中にダミーファイルを数個) |
| テストユーザー | 部署ごとに最低1名ずつ、合計2〜3名分のローカルユーザーアカウント |
| ネットワーク | 同一ネットワーク内で共有フォルダにアクセスできる状態(仮想マシン間の共有でも可) |

- [ ] 検証用の仮想マシンまたは実機を用意した
- [ ] 部署ごとのテスト用フォルダを作成した
- [ ] 部署ごとのテスト用ユーザーアカウントを作成した

## 作業目的(ゴール)

営業部・経理部それぞれの共有フォルダに対して、**自部署のメンバーだけがアクセスでき、他部署からは一切見えない状態**を作ります。具体的には以下を実現します。

- 部署ごとのグループを作成し、ユーザーを正しく所属させる
- 共有アクセス許可・NTFSアクセス許可の両方をグループ単位で正しく設定する
- 不要に残っている広範囲の権限(Everyoneなど)を取り除く
- 実際にテストユーザーでログインし、意図した通りにアクセス制御されていることを確認する

## 作業手順(詳細)

### 手順1: 共有アクセス許可とNTFSアクセス許可の違いを理解する

NTFS(NT File System。Windowsで標準的に使われているファイルシステム=データの保存形式)環境でファイルを共有する場合、性質の異なる2つの権限が関わってきます。以降、この文書では「共有アクセス許可」を**共有権限**、「NTFSアクセス許可」を**NTFS権限**と略して呼ぶこともあります。まずこの違いを整理しておきましょう。

| 項目 | 共有アクセス許可(共有権限) | NTFSアクセス許可(NTFS権限) |
|---|---|---|
| 効果が及ぶ範囲 | ネットワーク経由(`\\サーバー名\共有名`)でアクセスした場合のみ | ローカルログオン・ネットワークアクセスの両方に適用 |
| 設定場所 | フォルダのプロパティ→「共有」タブ | フォルダのプロパティ→「セキュリティ」タブ |
| 権限の粒度 | フルコントロール/変更/読み取り、の大まかな3種類 | フルコントロール/変更/読み取りと実行/フォルダーの内容の一覧表示/読み取り/書き込み、など細かく指定可能 |
| 設定できるファイルシステム | FAT32でも設定可能 | NTFS(またはReFS)でフォーマットされたドライブのみ |

つまり、共有アクセス許可は「建物の玄関の鍵」、NTFSアクセス許可は「各部屋のドアの鍵」のようなイメージです。玄関の鍵(共有)が開いていても、部屋のドア(NTFS)に鍵がかかっていれば入れませんし、その逆も同じです。この関係は、後ほど紹介する「共有権限 × NTFS権限 = 実効権限」という暗記法とセットで覚えておくと忘れにくくなります。

### 手順2: 最重要原則を理解する「厳しい方が勝つ」

共有アクセス許可とNTFSアクセス許可がネットワーク経由でのアクセス時にぶつかった場合、**より制限の厳しい方が実際に適用されます**。この「最終的にユーザーが持つことになる権限」のことを**実効権限(じっこうけんげん)**と呼びます。これはトラブルシューティングで最も重要な原則です。

| 共有権限 | NTFS権限 | 実際に適用される権限(実効権限) |
|---|---|---|
| フルコントロール | 読み取りのみ | 読み取りのみ |
| 変更 | フルコントロール | 変更 |
| 読み取りのみ | フルコントロール | 読み取りのみ |
| フルコントロール | フルコントロール | フルコントロール |

この表からわかる通り、**片方だけをフルコントロールにしても、もう片方が緩くない限り実効権限は上がりません**。今回のトラブルも、この原則を理解していれば冷静に切り分けができます。

### 手順3: 現状のアクセス許可をGUIで確認する

1. 対象フォルダを右クリックし、「プロパティ」を開きます。
2. 「共有」タブを開き、「共有(S)」ボタン(または「詳細な共有」→「アクセス許可」)から、共有アクセス許可に誰がどの権限で登録されているかを確認します。
3. 「セキュリティ」タブを開き、「編集(E)」ボタンからNTFSアクセス許可の登録内容を確認します。
4. 「セキュリティ」タブの「詳細設定」→「実効アクセス」タブを使うと、特定のユーザーが実際に持つ実効権限をシミュレーションできます。原因調査にとても便利な機能なので覚えておきましょう。

### 手順4: コマンドで共有フォルダの一覧を確認する

GUIだけでなくコマンドでも確認できるようにしておくと、リモート作業や自動化の際に役立ちます。

```powershell
net share
```

特定の共有だけを確認したい場合は、共有名を指定します。

```powershell
net share 営業部共有
```

このコマンドで、共有名・パス・現在登録されているコメントなどを確認できます。

### 手順5: コマンドでNTFSアクセス許可を確認する

`icacls`(NTFSのアクセス制御リスト=ACLを表示・変更するコマンド)を使ってフォルダの権限を確認します。

```powershell
icacls "D:\Shared\営業部"
```

実行結果には、ユーザーやグループ名の後ろに次のような略号が表示されます。

| 略号 | 意味 |
|---|---|
| `(F)` | フルコントロール(Full control) |
| `(M)` | 変更(Modify) |
| `(RX)` | 読み取りと実行(Read & eXecute) |
| `(R)` | 読み取り(Read) |
| `(W)` | 書き込み(Write) |
| `(OI)` | オブジェクト継承(ファイルに権限を継承させる) |
| `(CI)` | コンテナ継承(サブフォルダに権限を継承させる) |

`F → M → RX → R → W` の順に「頭文字」を思い浮かべると、権限の強さの序列も一緒に覚えられます。

### 手順6: 原因を特定する

手順3〜5で確認した内容をもとに、原因を切り分けます。今回のようなケースでは、次の3つのいずれか(または複数)が組み合わさっていることが典型的です。それぞれの具体的な対処法は、後述の「よくあるエラーと対処法」も合わせて参照してください。

- 共有アクセス許可とNTFSアクセス許可のどちらか一方だけが厳しく設定されている
- 「Everyone」グループ(認証の有無を問わず事実上すべてのユーザーが含まれる、非常に範囲の広い既定グループ)に広く権限が残っている
- 対象ユーザーが本来所属すべき部署グループに入っていない、あるいは間違ったグループに入っている

### 手順7: 部署ごとのグループを設計・作成する

個人単位で権限を設定すると管理が煩雑になり、ミスの元になります。**「グループに権限を与え、ユーザーをグループに所属させる」**のが基本方針です。

```powershell
net localgroup 営業部 /add
net localgroup 経理部 /add
```

作成したグループに、該当するユーザーを追加します。

```powershell
net localgroup 営業部 sato_taro /add
net localgroup 経理部 suzuki_hanako /add
```

### 手順8: NTFSアクセス許可をグループ単位で設定する

まず、意図せず残っている広い権限を削除します。ユーザー名やグループ名にスペースが含まれる場合に備えて、常にダブルクォートで囲むのがおすすめです。

```powershell
icacls "D:\Shared\営業部" /remove "Everyone"
```

続いて、部署グループに対して適切な権限を付与します。`(OI)(CI)` を付けることで、以後作成されるサブフォルダ・ファイルにも権限が引き継がれます。

```powershell
icacls "D:\Shared\営業部" /grant "営業部:(OI)(CI)M"
icacls "D:\Shared\経理部" /grant "経理部:(OI)(CI)M"
```

他部署のグループには権限を付与しないことで、経理部グループが営業部フォルダを見られない状態を作ります。

> **つまずきやすいポイント**: `/remove` を実行しても一覧から消えない場合、その権限が親フォルダから**継承**されている可能性があります。その場合は `icacls "パス" /inheritance:r` で継承を解除(既存の継承エントリを削除し、明示的な設定に切り替え)してから、必要な権限を改めて付与してください。

### 手順9: 共有アクセス許可をグループ単位で設定する

PowerShellの`SmbShare`モジュール(Windows標準搭載の、共有フォルダをコマンドで管理するための機能)を使うと、共有アクセス許可もコマンドから設定できます。

```powershell
Grant-SmbShareAccess -Name "営業部共有" -AccountName "営業部" -AccessRight Change -Force
Revoke-SmbShareAccess -Name "営業部共有" -AccountName "Everyone" -Force
```

GUI操作に慣れている場合は、共有タブの「アクセス許可」画面から同様の設定を行っても構いません。大切なのは**共有側・NTFS側の両方を、同じグループを対象に見直す**ことです。

### 手順10: 実際にログインして動作確認する

設定変更後は、必ずテストユーザーで動作確認を行います。

1. 経理部のテストユーザーでログインし、営業部の共有フォルダにアクセスできない(拒否される)ことを確認する。
2. 営業部のテストユーザーでログインし、自部署の共有フォルダに読み書きできることを確認する。
3. グループ変更を反映させるため、テストユーザーは一度ログオフ・再ログオンしてから確認する(Windowsはログオン時に、そのユーザーが持つ権限情報である**トークン**にグループ所属を記録し、ログオン中は更新しないため)。

**ワンポイント**: 対象ユーザーで実際にログオンした状態で `whoami /groups` を実行すると、そのユーザーが現在所属しているグループの一覧を確認できます。グループ変更が正しく反映されているかのチェックに便利です。

```powershell
whoami /groups
```

- [ ] 共有アクセス許可を確認・修正した

## よくあるエラーと対処法

| 症状 | 原因 | 対処法 |
|---|---|---|
| 共有はフルコントロールなのに書き込めない | NTFSアクセス許可が「読み取り」のみになっている | `icacls` でNTFS側の権限を確認し、必要な範囲まで「変更」以上に引き上げる |
| 他部署のファイルが丸見え | Everyoneグループに共有・NTFSどちらか(または両方)の権限が広く残っている | `icacls /remove "Everyone"` や共有アクセス許可の見直しで削除する |
| `/remove` してもEveryoneが消えない | 親フォルダから権限を継承している | `icacls "パス" /inheritance:r` で継承を解除してから権限を再設定する |
| 権限変更したのに反映されない | ユーザーが変更前のログオンセッションのまま(トークンにグループ情報がキャッシュされている) | 一度ログオフ・再ログオンしてもらう。`whoami /groups` で反映状況を確認する |
| 新しく作ったファイルにだけ権限が効かない | `icacls` の付与時に `(OI)(CI)` の継承指定を忘れている、または既存の配下ファイルに反映していない | 継承フラグを付けて再設定するか、`/T` オプションで既存の配下にも一括反映する |

## 覚えておきたいポイント(暗記のコツ)

- **「共有権限 × NTFS権限 = 実効権限(厳しい方が勝つ)」**という掛け算のイメージで覚えましょう。どちらか片方だけを見て「フルコントロールになっているから大丈夫」と判断するのはNGです。必ず**共有タブとセキュリティタブの両方**を確認する癖をつけてください。
- 手順1で紹介した「玄関の鍵(共有)」と「部屋の鍵(NTFS)」の例えとセットで思い出すと、掛け算の意味がイメージしやすくなります。
- `icacls` の略号は強い順に `F(フルコントロール) > M(変更) > RX(読み取りと実行) > R(読み取り) > W(書き込み)` です。頭文字の英単語(Full / Modify / Read&eXecute)と一緒に覚えると忘れにくくなります。
- 継承フラグは「O=オブジェクト(ファイル)」「C=コンテナ(フォルダ)」の頭文字、と覚えると `(OI)` `(CI)` の意味を思い出しやすくなります。
- 権限はユーザー個人ではなく**部署グループ単位**で管理するのが鉄則です。人の異動や入退社があっても、グループへの出し入れだけで対応できるようにしておくと、運用がぐっと楽になります。

## 振り返り・発展課題

- 今回はローカルグループ・ローカルユーザーで練習しましたが、実際の企業ではActive Directory(組織内のユーザー・コンピューターを一元管理する仕組み)のドメイングループを使うのが一般的です。ADの管理コンソールでグループを作成する練習にも挑戦してみましょう。余裕があれば、ユーザーをグローバルグループに、それをドメインローカルグループに入れてリソースへ権限を割り当てる「AGDLP」と呼ばれる設計パターンについても調べてみると、より実務に近い理解が得られます。
- 「実効アクセス」タブを使った権限診断を、別のユーザー・別のフォルダでも試してみましょう。
- NTFSの監査機能(誰がいつファイルにアクセスしたかを記録する機能)を有効化し、不正アクセスの追跡ができるようにしてみましょう。
- 複数のファイルサーバーをまたいで共有フォルダを一元管理できる「DFS名前空間」についても調べてみると、より実務に近い知識が身につきます。

## ポートフォリオへの書き方例

> **共有フォルダのアクセス権不具合対応**
> 部署間で共有フォルダの閲覧範囲が意図せず広がっていた問題に対し、共有アクセス許可とNTFSアクセス許可を切り分けて調査。原因を「Everyoneグループへの権限残存」と特定し、部署単位のグループを再設計のうえ`icacls`コマンドで是正。実際にテストユーザーでログイン検証を行い、他部署からの閲覧不可・自部署内での正常な読み書きを確認した。
