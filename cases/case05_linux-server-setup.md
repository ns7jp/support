# 案件05: Linuxサーバー初期構築案件(Ubuntu Server)

**レベル**: 初級〜中級 ｜ **目安時間**: 3〜4時間

## 案件カテゴリ

サーバー構築 / Linux基盤構築 / セキュリティ基礎

Linuxサーバーを新規に構築する際に必ず行う「初期設定」をひととおり体験できる案件です。サーバー構築エンジニアの実務では、OSをインストールしただけの状態から、安全に運用できる状態(セキュアな初期構築、「ハードニング」とも呼ばれます)に整えるまでが最初の重要な仕事になります。

## この案件で身につくスキル

- [ ] ホスト名・タイムゾーンなど、Linuxサーバーの基本情報の設定
- [ ] 一般ユーザーの作成と`sudo`(一般ユーザーが一時的に管理者権限でコマンドを実行できる仕組み)権限の付与
- [ ] SSH(Secure Shell。ネットワーク越しにサーバーを安全に遠隔操作するための仕組み)の鍵認証設定
- [ ] `sshd_config`(SSHサーバーの動作を定義する設定ファイル)によるセキュリティ強化(パスワード認証無効化・root禁止)
- [ ] `ufw`(Uncomplicated Firewall。Linuxのファイアウォールを簡単に操作するためのツール)による通信制御
- [ ] `apt`コマンドによるパッケージ(OS上で動くソフトウェアの部品)管理の基礎

## 想定シナリオ(依頼内容)

> 「新しい社内システムを検証するために、Linuxサーバーを1台用意してほしいです。OSはUbuntu Serverで問題ありません。パスワードだけでログインできる状態はセキュリティ的に不安なので、SSHの鍵認証でログインできるようにしてください。また、rootユーザーで直接ログインできないようにし、ファイアウォールでSSH以外のポートは閉じておいてもらえますか。」

クライアントからの要望を整理すると、次の4点が要件になります。

1. Ubuntu Serverが動作するサーバーを1台用意する
2. 一般ユーザーで管理作業ができ、鍵認証のみでSSHログインできる
3. root直接ログインとパスワードログインを禁止する
4. ファイアウォールでSSH以外の通信を遮断する

## 事前準備・必要な環境

- [ ] 仮想化ソフト(VirtualBoxやVMwareなど)、またはクラウドサービス(検証用の小規模インスタンスなど)でUbuntu Serverを起動できる環境
- [ ] Ubuntu Serverのインストールメディア、またはクラウドの標準イメージ(いずれも公式サイトから入手します)
- [ ] 作業用PC(WindowsでもmacOSでもLinuxでも可)
- [ ] 作業用PCにSSHクライアントが使えること(WindowsはPowerShellやTeraTerm、macOS/Linuxは標準のターミナルでOKです)
- [ ] サーバーと作業用PCがネットワーク的に通信できる状態(同一ネットワーク、または疎通確認済みのVPCなど)
- [ ] サーバー側でOpenSSHサーバー(SSH接続を受け付けるサーバー側のソフトウェア)が動作していること。Ubuntu Serverのインストール時に「Install OpenSSH server」を選択していれば自動的に有効になります。未確認の場合はコンソールから`sudo systemctl status ssh`で稼働状況を確認し、動いていなければ`sudo apt install openssh-server`でインストールします
- [ ] サーバーのOSインストールが完了し、初回ログインができる状態

> ポイント:この案件はコンソール(仮想マシンの画面、あるいはクラウドのシリアルコンソール)に直接アクセスできる状態で行ってください。SSH設定を誤ると、一時的にSSH接続ができなくなることがあるためです。コンソールが使えれば、万一の際もそこから復旧できます。

## 作業目的(ゴール)

以下の状態を作ることが今回のゴールです。

- 一般ユーザーで`sudo`を使って管理者権限のコマンドを実行できる
- SSH鍵認証でサーバーにログインでき、パスワードでのログインはできない
- rootユーザーでの直接SSHログインができない
- `ufw`が有効化されており、SSH(22番ポート)以外の通信は遮断されている
- OSのパッケージが最新の状態に更新されている

## 作業手順(詳細)

作業は大きく分けて次の10ステップです。細かい注意点は多いですが、流れ自体はシンプルなので、まず全体像をつかんでから取り掛かりましょう。

1. ホスト名の設定
2. タイムゾーンの設定
3. パッケージの更新
4. 一般ユーザーの作成とsudo権限の付与
5. SSH鍵ペアの作成(作業用PC側)
6. 公開鍵をサーバーに配置する
7. 鍵認証でログインできるか確認する
8. `sshd_config`の編集(パスワード認証無効化・root禁止)
9. 別のターミナルで新しい設定でのログインを確認する
10. `ufw`でファイアウォールを設定する

### 1. ホスト名の設定

サーバーの名前(ホスト名)を、用途がわかりやすいものに変更します。

```bash
sudo hostnamectl set-hostname web-verify01
```

`hostnamectl`はホスト名やOSの基本情報を管理するコマンドです。設定できているか確認します。

```bash
hostnamectl
```

### 2. タイムゾーンの設定

ログの時刻がずれるとトラブル調査に支障が出るため、タイムゾーンを日本時間に合わせます。`timedatectl`はシステムの日時・タイムゾーンを管理するコマンドです。

```bash
sudo timedatectl set-timezone Asia/Tokyo
timedatectl
```

`Time zone: Asia/Tokyo`と表示されていればOKです。

### 3. パッケージの更新

OSインストール直後は、パッケージ(OS上で動くソフトウェアの部品)が古い場合が多いので、最新化しておきます。

```bash
sudo apt update
sudo apt upgrade -y
```

`apt update`はパッケージ一覧を最新化するだけの処理、`apt upgrade`が実際にパッケージを更新する処理です。この2つはセットで覚えましょう。

> 補足:`apt upgrade`の実行結果に「A reboot is required」のようなメッセージが表示された場合は、カーネルなど再起動が必要な更新が含まれています。今回の検証手順を続けても問題ありませんが、実務では区切りの良いタイミングで`sudo reboot`しておくと安全です。

### 4. 一般ユーザーの作成とsudo権限の付与

rootユーザーで日常作業を行うのは事故のもとなので、作業用の一般ユーザーを作成します。

```bash
sudo adduser demouser
```

対話形式でパスワードなどを聞かれるので入力します。続けて、`sudo`グループに追加して管理者コマンドを実行できるようにします。

```bash
sudo usermod -aG sudo demouser
```

`-aG`は「既存の所属グループを維持したまま(append)、指定グループ(Group)に追加する」という意味のオプションです。`-a`を忘れると他のグループから外れてしまうことがあるため注意してください。

所属グループを確認しておきましょう。

```bash
groups demouser
```

`sudo`が表示されていれば成功です。

### 5. SSH鍵ペアの作成(作業用PC側)

ここからは**作業用PC側**の操作です。サーバーではなく、自分の手元のPCでコマンドを実行します。

```bash
ssh-keygen -t ed25519 -C "demouser-key"
```

- `-t ed25519`:鍵の方式の指定です。現在推奨されている、安全性と速度のバランスが良い方式です。
- `-C`:鍵にわかりやすいコメントを付けられるオプションです(任意)。

保存先を聞かれたらそのままEnter(既定値)で問題ありません。パスフレーズ(鍵自体を保護する追加のパスワード)の設定も聞かれますが、検証用途でも設定しておくことを推奨します(パスフレーズを設定すると、ログインのたびにその入力が求められるようになります)。

これで秘密鍵(自分だけが持つ鍵。`id_ed25519`)と公開鍵(サーバーに渡す鍵。`id_ed25519.pub`)のペアが作成されます。

### 6. 公開鍵をサーバーに配置する

公開鍵をサーバーに登録すれば、鍵認証でログインできるようになります。最も簡単なのは`ssh-copy-id`コマンドです。

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub demouser@<サーバーのIPアドレス>
```

このコマンドは、パスワード認証でサーバーに一時的にログインし、公開鍵を適切な場所・適切な権限で自動的に配置してくれる便利なコマンドです(まだパスワード認証を無効化する前の段階で使います)。

`ssh-copy-id`が使えない環境(一部のWindows環境など)の場合は、以下のように手動で設定することもできます。まず作業用PC側で公開鍵の中身を表示します。

```bash
cat ~/.ssh/id_ed25519.pub
```

表示された`ssh-ed25519 AAAA...`で始まる1行をすべてコピーしておきます。次に、サーバー側に一度パスワードでログインしたうえで、以下を実行してください。

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
echo "先ほどコピーした公開鍵の内容をここに貼り付け" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

`authorized_keys`は「このユーザーへのログインを許可する公開鍵の一覧」を記録するファイルです。パーミッション(アクセス権限)の設定は非常に重要です。緩いままだとSSH側が「安全でない」と判断し、鍵認証を拒否してしまいます。

### 7. 鍵認証でログインできるか確認する

作業用PCから鍵を使ってログインしてみます。

```bash
ssh -i ~/.ssh/id_ed25519 demouser@<サーバーのIPアドレス>
```

パスワードを聞かれずにログインできれば成功です(パスフレーズを設定した場合はそちらの入力は求められます)。

**重要**:この時点ではまだパスワード認証を無効化せず、必ず鍵認証で問題なくログインできることを確認してから次のステップに進んでください。

### 8. sshd_configの編集(パスワード認証無効化・root禁止)

鍵認証でのログインが確認できたら、SSHサーバーの設定を変更します。**このステップ7で使っている、鍵認証でログイン中のSSHセッションは、次のステップ9で新しい設定での動作確認が終わるまで絶対に閉じないでください。** 万一設定を誤って接続できなくなっても、このセッションが生きていればそこから復旧できます。

同じセッションのまま、設定ファイルを編集します。

```bash
sudo nano /etc/ssh/sshd_config
```

以下の項目を探して(なければ追記して)、値を変更します。

```text
PermitRootLogin no
PasswordAuthentication no
```

保存したら、設定ファイルの文法にエラーがないかを必ず確認します。`-t`は設定ファイルの文法だけをテストするオプションで、実際の設定は変更しません。

```bash
sudo sshd -t
```

何も表示されなければ文法エラーはありません。問題なければSSHサービスを再起動して設定を反映します。

```bash
sudo systemctl restart ssh
```

> 補足1:Ubuntuでは、SSHサービスのユニット名は`ssh`です(CentOSなど他のディストリビューションでは`sshd`という名前が使われることが多いので、混同しないよう注意してください)。
>
> 補足2:`restart`を実行しても、今つながっている(接続済みの)SSHセッションが強制的に切断されることはありません。新しい設定が適用されるのは、この後**新しく**接続する際からです。だからこそ、今のセッションを閉じずに次のステップで動作確認を行います。

### 9. 別のターミナルで新しい設定でのログインを確認する

現在のセッション(ステップ7から開いたままのもの)は閉じずに、**新しく別のターミナルを開いて**、鍵認証でログインし直せるかを確認します。

```bash
ssh -i ~/.ssh/id_ed25519 demouser@<サーバーのIPアドレス>
```

新しいターミナルからログインできたら成功です。ここで初めて、最初のセッションを閉じても安全な状態になります。もし新しいターミナルからログインできない場合は、最初のセッションはまだ生きているはずなので、それを使って`sshd_config`の内容を見直してください。

### 10. ufwでファイアウォールを設定する

最後にファイアウォールを設定します。**ここが最も事故の起きやすいポイントです。**

まず、SSH接続を許可するルールを先に追加します。

```bash
sudo ufw allow OpenSSH
```

`OpenSSH`はufwにあらかじめ用意されているアプリケーションプロファイルで、22番ポート(TCP)を許可する設定と同じ意味です。`sudo ufw allow 22/tcp`と書いても同じ結果になります。

ルールが登録されたことを確認してから、ufwを有効化します。

```bash
sudo ufw enable
```

有効化後、設定内容を確認します。`verbose`は詳細情報を表示するオプションです。

```bash
sudo ufw status verbose
```

`22/tcp`が`ALLOW`になっており、ステータスが`active`になっていれば完了です。

## 完了確認チェックリスト

- [ ] 一般ユーザーで`sudo`が使える(`sudo whoami`を実行すると`root`と表示される)
- [ ] SSH鍵認証でログインできる(`ssh -i ~/.ssh/id_ed25519 demouser@<サーバーのIPアドレス>`でパスワードを聞かれずにログインできる)
- [ ] パスワード認証が無効化されている(鍵を指定せず`ssh demouser@<サーバーのIPアドレス>`を実行すると接続を拒否される)
- [ ] rootの直接ログインが禁止されている(`ssh root@<サーバーのIPアドレス>`を実行すると接続を拒否される)
- [ ] `ufw`が有効でSSH以外の通信が閉じている(`sudo ufw status verbose`で`Status: active`かつ`22/tcp`のみ`ALLOW`と表示される)
- [ ] OSのパッケージが最新化されている(`sudo apt update && sudo apt list --upgradable`で更新対象がない、または少ない)

## よくあるエラーと対処法

| 事象 | 主な原因 | 対処法 |
|---|---|---|
| `Permission denied (publickey)`と表示されログインできない | `.ssh`ディレクトリや秘密鍵・`authorized_keys`のパーミッションが緩い | `chmod 700 ~/.ssh`、`chmod 600 ~/.ssh/authorized_keys`、秘密鍵は`chmod 600 ~/.ssh/id_ed25519`に設定し直す |
| `ufw enable`後に自分自身がSSH接続できなくなった | SSH許可ルールを追加する前に`ufw enable`してしまい、22番ポートも閉じられた | コンソール(仮想マシン画面など)からログインし、`sudo ufw allow OpenSSH`を実行後、`sudo ufw reload`または再度`enable`する。最悪の場合は`sudo ufw disable`で一時的に無効化して復旧する |
| `sshd_config`を編集したのに設定が反映されない | 編集後に`systemctl restart ssh`を忘れている | `sudo systemctl restart ssh`を実行し、`sudo systemctl status ssh`で稼働状況を確認する |
| SSH自体に接続できない(`Connection refused`など) | OpenSSHサーバーが未インストール・未起動、またはufwでポートが閉じている | `sudo systemctl status ssh`でサービス状態を確認し(なければ`sudo apt install openssh-server`)、`sudo ufw status`でポートの許可状況も確認する |
| `sshd_config`編集後にSSHサービスが起動しない | 設定ファイルに文法ミスがある | `sudo sshd -t`で事前に文法チェックを行う習慣をつける |

## 覚えておきたいポイント(暗記のコツ)

- **鉄則**:「`ufw`を有効にする前に、必ずSSHの許可を先に出す」。順番を間違えると、自分自身をサーバーから締め出す(ロックアウトする)事故につながります。「先に鍵(SSH許可)を用意してから、玄関(ファイアウォール)を閉める」とイメージすると忘れにくいです。「許可(allow)→有効化(enable)」の順番を体に染み込ませましょう。
- パーミッションの数字は「読む(4)+書く(2)+実行(1)」の足し算です。

  | 数字 | 内訳 | 意味 |
  |---|---|---|
  | 7 | 4+2+1 | 読み・書き・実行すべて可能 |
  | 6 | 4+2 | 読み書きのみ可能(実行は不可) |
  | 0 | なし | 権限なし |

  これを踏まえて「フォルダ(`.ssh`)は700、ファイル(秘密鍵・`authorized_keys`)は600」と覚えます。鍵ファイルは「実行するもの」ではないので実行権(1)は不要、という理屈まで理解しておくと忘れにくくなります。
- 設定変更は「編集 → 文法チェック(`sshd -t`)→ 再起動 → 別セッションで動作確認 → 元のセッションを閉じる」という流れを毎回徹底すると事故を防げます。`restart`しても今の接続は切れないので、確認が終わるまで元のセッションは開いたままにするのがコツです。
- `usermod -aG`の`-a`は「Append(追記・追加)」の頭文字です。「Append to Group」と覚えておくと、`-a`を付け忘れて他のグループ所属が消えてしまう事故を防げます。

## 振り返り・発展課題

初期構築が一通りできたら、次のような発展課題にも挑戦してみましょう。

- SSHの待受ポートを22番以外に変更し、ufwのルールも合わせて変更してみる
- `fail2ban`(不正なログイン試行を自動的に検知してブロックするツール)を導入し、ブルートフォース攻撃対策を強化する
- 複数人での運用を想定し、ユーザーごとに異なる公開鍵を登録する運用ルールを考えてみる
- 今回手作業で行った設定を、Ansibleなどの構成管理ツールで自動化してみる
- クラウド環境(セキュリティグループなど)とufwを併用する場合の役割分担を整理してみる
