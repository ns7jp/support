# 案件10: セキュリティインシデント対応案件(不審ログイン調査)

## 案件カテゴリ

運用保守・セキュリティインシデント対応(インシデントレスポンス)

## この案件で身につくスキル

- インシデント対応の基本的な進め方(事実確認→影響範囲の切り分け→一時対応→恒久対策→報告)
- Linuxのログファイルを使った侵入調査の基礎(`/var/log/auth.log`、`last`、`lastb`など)
- 不審なアカウント・IPアドレスへの一時対応(アカウントロック、ファイアウォールでの遮断)
- ブルートフォース攻撃(総当たり攻撃。パスワードや暗証番号を片っ端から試して突破しようとする攻撃)対策としてのfail2ban(一定回数ログインに失敗した相手を自動でブロックしてくれるツール)の導入
- SSHの鍵認証への統一、パスワードポリシー強化などの恒久対策
- 非エンジニアにも伝わるインシデント報告書の作成

## 想定シナリオ(依頼内容)

案件05で構築・運用しているLinuxサーバー(Ubuntu Serverを想定)について、クライアントから次のような連絡が入りました。

> 「監視ツールから『サーバーへの不審なログイン試行が多発している』というアラートが届きました。何が起きているのか確認して、必要な対応をお願いします。今日中に状況を報告してもらえますか。」

不審なログインは、放置すると不正アクセスによる情報漏えいやサーバーの乗っ取りにつながる可能性がある、優先度の高い一次対応(インシデントが発生した際、最初に行う応急的な対応)案件です。落ち着いて型どおりに進めれば未経験の方でも十分に対応できる内容ですので、本ドキュメントでは実際に手を動かしながら「事実確認→応急処置→恒久対策→報告」までの一連の流れを体験します。

## 事前準備・必要な環境

- [ ] 案件05で構築したLinuxサーバー(Ubuntu Server想定)にSSH接続できること
- [ ] サーバーの管理者権限(sudoコマンドが使えるアカウント)
- [ ] ターミナルソフト(Windowsの場合はTeraTermやWindows Terminalなど)
- [ ] `grep`、`tail`など基本的なLinuxコマンドの操作経験(案件01〜05相当の知識)
- [ ] メモ帳やMarkdownエディタ(報告書作成用)

> 補足: 本ドキュメントでは検証用に架空のIPアドレス`192.0.2.100`(ドキュメント用に予約された非実在アドレスです)を例として使用します。実際の作業では、ご自身の監視ログに記録された実際の送信元IPアドレスに読み替えてください。

## 作業目的(ゴール)

- ログから「実際に何が起きたのか」を事実ベースで確認できるようになる
- 影響を受けたアカウント・データの有無を切り分けられるようになる
- 攻撃を止めるための一時対応(応急処置)を実施できるようになる
- 同じ攻撃が再発しないための恒久対策を実施できるようになる
- 対応内容を第三者にも伝わる報告書としてまとめられるようになる

## 作業手順(詳細)

インシデント対応は「思いつきで動く」のではなく、決まった型に沿って進めることが重要です。ここでは **事実確認 → 影響範囲の切り分け → 一時対応 → 恒久対策 → 報告** の5ステップで進めます。工程は多く見えますが、1つずつ順番にこなせば迷うことはありません。実際の現場でもこの型がそのまま使えますので、じっくり体験してみましょう。

### ステップ1: 事実確認(ログを見て何が起きたかを把握する)

まずはサーバーにSSH接続し、認証ログを確認します。Ubuntu/Debian系では認証関連のログは`/var/log/auth.log`に記録されます(RHEL/CentOS系では`/var/log/secure`が該当します)。

```bash
# 直近の認証ログを確認する
sudo tail -n 200 /var/log/auth.log

# ログイン失敗(パスワード不一致)だけを抽出する
sudo grep "Failed password" /var/log/auth.log

# 存在しないユーザー名でのログイン試行を抽出する
sudo grep "Invalid user" /var/log/auth.log
```

次に、実際にログインが成功した履歴を`last`コマンドで確認します。

```bash
# ログイン成功の履歴を新しい順に表示する(-iでIPアドレス表示)
last -i

# 現在ログイン中のユーザーを確認する
who
w
```

失敗したログイン試行の履歴は`lastb`コマンドでも確認できます(`/var/log/btmp`というファイルを参照するコマンドで、権限がないと表示できない場合はsudoを付けます)。

```bash
sudo lastb | head -n 50
```

systemd(多くのLinuxディストリビューションで使われるサービス管理の仕組み)を採用している環境では、`journalctl`(systemdが記録するログをまとめて検索・表示できるコマンド)でSSHサービスのログを横断的に検索することも可能です(Ubuntuではサービス名が`ssh`、RHEL系では`sshd`です)。

```bash
sudo journalctl -u ssh --since "2026-08-29" | grep -i "fail"
```

これらのログから、「いつ・どのIPアドレスから・どのユーザー名で・何回」ログイン試行が行われたかを事実として記録しておきましょう。

### ステップ2: 影響範囲の切り分け

事実確認で「攻撃があった」ことがわかっても、それだけでは対応は終わりません。次に確認すべきは「実際に突破されたかどうか」です。

- [ ] 攻撃対象になったアカウントで、ログインが**成功**している形跡はないか(`last -i`の結果を確認)
- [ ] ログインが成功していた場合、そのアカウントの操作履歴(シェルの`history`ファイルや`sudo`の実行ログ)に不審な操作がないか
- [ ] 重要な設定ファイルやWebコンテンツが改ざんされていないか(タイムスタンプの確認例は以下)

```bash
# 直近1日以内に変更されたファイルを検索する(改ざんの痕跡確認)
sudo find /etc /var/www -mtime -1 -type f
```

- [ ] 攻撃対象になったアカウント以外にも、同じパスワードを使い回しているアカウントがないか

ここまでで「侵入は防げていたのか、実際に突破されたのか」を切り分けます。この切り分けの結果によって、次の一時対応の強さ(緊急度)が変わります。

### ステップ3: 一時対応(応急処置)

攻撃が続いている、あるいは突破の疑いがある場合は、まず被害の拡大を止めます。

| 対応内容 | コマンド例 | 注意点 |
|---|---|---|
| 該当アカウントの一時ロック | `sudo passwd -l ユーザー名`<br>または`sudo usermod -L ユーザー名` | ロック解除は`passwd -u`または`usermod -U` |
| 該当IPアドレスの遮断 | `sudo ufw deny from 192.0.2.100` | ufw(Ubuntu標準のファイアウォール管理ツール)導入済みの場合 |
| SSH経由の遮断(ufw未導入時) | `sudo iptables -A INPUT -s 192.0.2.100 -j DROP` | iptables(Linux伝統のファイアウォール制御コマンド)。設定は再起動で消えるため恒久対策ではない |

```bash
# 該当アカウントを一時的にロックする
sudo passwd -l suspicious_user

# 攻撃元IPアドレスからの通信を拒否する(ufwの場合)
sudo ufw deny from 192.0.2.100

# 設定が反映されているか確認する
sudo ufw status numbered
```

> 注意: ここで最も起きやすい失敗が「正規ユーザーを誤ってブロックしてしまう」ことです。ロックやブロックの前に、そのアカウント・IPアドレスが業務で利用中でないか、必ずクライアントや関係者に確認しましょう。

### ステップ4: 恒久対策(再発防止)

一時対応はあくまで応急処置です。同じ攻撃が繰り返されないよう、恒久対策まで実施して初めてインシデント対応は完了します。

**(1) fail2banの導入**

fail2ban(ログを監視して、一定回数以上ログインに失敗した送信元IPアドレスを自動的に一定時間ブロックしてくれるツール)を導入すると、ブルートフォース攻撃を自動で防げるようになります。

```bash
# fail2banをインストールする
sudo apt update
sudo apt install fail2ban -y

# 設定ファイルをコピーして自分用の設定ファイルを作る(元ファイルは直接編集しない)
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
```

`jail.local`内の`[sshd]`セクションを次のように編集します。

```ini
[sshd]
enabled = true
# 何回失敗したらブロック対象にするか
maxretry = 5
# 失敗回数をカウントする時間(秒)
findtime = 600
# ブロックする時間(秒)
bantime = 3600
```

編集後は再起動して反映します。

```bash
sudo systemctl restart fail2ban
sudo systemctl enable fail2ban

# sshd用のjailの状態を確認する
sudo fail2ban-client status sshd
```

**(2) パスワード認証の廃止・鍵認証への統一**

パスワード認証は総当たり攻撃の標的になりやすいため、SSH鍵認証(公開鍵と秘密鍵のペアを使ってログインする、パスワードより安全な認証方式)へ統一します。

```bash
# クライアント側で鍵ペアを作成する(まだ作っていない場合)
ssh-keygen -t ed25519

# 作成した公開鍵をサーバーに登録する
ssh-copy-id ユーザー名@サーバーのIPアドレス
```

鍵での接続確認ができたら、サーバー側の`/etc/ssh/sshd_config`を編集します。

```ini
# パスワードでのログインを禁止し、鍵認証のみ許可する
PasswordAuthentication no
# rootユーザーでの直接SSHログインを禁止する
PermitRootLogin no
```

> 重要: 設定変更後にSSHサービスを再起動する前に、**必ず今の接続を切らずに別のターミナルで新規接続テストを行ってください**。設定ミスに気づかずセッションを切ってしまうと、サーバーにログインできなくなる恐れがあります。

```bash
# 設定ファイルの文法エラーがないか確認する
sudo sshd -t

# 問題なければ再起動する
sudo systemctl restart sshd
```

**(3) パスワードポリシーの強化**

パスワード認証を残す場合や、他のサービスのアカウントについては、`chage`(アカウントのパスワード有効期限などを管理するコマンド)を使ってパスワードポリシーを強化します。

```bash
# パスワードの有効期限を90日に設定する
sudo chage -M 90 ユーザー名

# 現在のパスワードポリシーを確認する
sudo chage -l ユーザー名
```

さらに`libpam-pwquality`(パスワードの複雑さをチェックする認証モジュール)を導入すると、`/etc/pam.d/common-password`で最小文字数や複雑さ(大文字・数字・記号の必須化など)を強制できます。

```bash
sudo apt install libpam-pwquality -y
```

### ステップ5: 報告(インシデント報告書の作成)

最後に、対応内容をまとめて報告書として提出します。口頭だけの報告は、後で「言った・言わない」のトラブルや、対応履歴の抜け漏れにつながるため避けましょう。以下は簡易フォーマットの例です。

```markdown
# インシデント報告書

## 発生日時
2026-08-30 03:12(検知アラート受信時刻)

## 検知経緯
監視ツールのアラートにより、SSHへの多数のログイン失敗を検知。

## 影響範囲
- 攻撃元IPアドレス: 192.0.2.100(例)
- 対象アカウント: suspicious_user
- ログイン成功の有無: なし(全て失敗、突破の形跡なし)
- データ・設定ファイルの改ざん: 確認されず

## 対応内容
- 該当アカウントを一時ロック
- 該当IPアドレスをufwで遮断
- fail2banを導入し、自動遮断ルールを設定
- SSHをパスワード認証から鍵認証へ変更
- 全アカウントにパスワード有効期限90日を設定

## 再発防止策
- fail2banによる自動ブロックの継続運用
- 月次でのログ棚卸し(定期監査)の実施
- 今後は多要素認証の導入を検討
```

## 完了確認チェックリスト

- [ ] ログから攻撃の事実を確認したか(いつ・どこから・何回)
- [ ] 影響を受けたアカウント・データがないか確認したか
- [ ] 一時対応(アカウントロックまたはIPブロック)を行ったか
- [ ] 恒久対策(fail2ban導入・鍵認証への統一・パスワードポリシー強化)を実施したか
- [ ] インシデント報告書を作成し、提出できる状態にしたか
- [ ] 正規ユーザー・正規IPアドレスを誤って遮断していないか再確認したか

## よくあるエラーと対処法

| 症状・失敗パターン | 原因 | 対処法 |
|---|---|---|
| ログ確認だけで満足し、対応が終わったと思ってしまう | 事実確認と恒久対策を混同している | 「事実確認はゴールではなくスタート」と意識し、必ず一時対応・恒久対策まで実施する |
| 正規ユーザーを誤ってブロック・ロックしてしまう | 遮断対象の確認を怠った | ロック・ブロック前に必ず利用者・利用時間帯を確認する。ロック後は速やかに関係者へ連絡する |
| 報告書を作らず口頭対応だけで終わらせる | 「直したから大丈夫」という思い込み | 対応が終わった時点で必ず報告書テンプレートに沿って文書化する習慣をつける |
| `sshd_config`編集後にSSH接続できなくなる | 設定ミスに気づかずセッションを切断した | 新しい接続で必ず先にログインテストを行ってから、元のセッションを閉じる |
| fail2ban導入後に自分自身がロックアウトされる | `maxretry`や自分のIPを除外し忘れた | `jail.local`の`ignoreip`に自分の作業用IPアドレスを追加しておく |

## 覚えておきたいポイント(暗記のコツ)

インシデント対応の5ステップは、それぞれの言葉の頭文字(先頭の1文字)を並べて **「事・範・応・恒・報(じ・はん・おう・こう・ほう)」** と覚えましょう。

- **事**実確認 → まずログで「何が起きたか」を確認する
- **範**囲の切り分け → 影響が及んだ範囲(アカウント・データ)を確認する
- **応**急対応(一時対応) → 被害拡大をいったん止める
- 恒**久**対策 → 同じ攻撃が起きないよう根本から直す
- **報**告 → 対応内容を文書化して共有する

まだ覚えにくいという方は、「病院の診療」にたとえるとイメージしやすくなります。

| インシデント対応 | 病院の診療にたとえると |
|---|---|
| 事実確認 | 問診・検査(何が起きているかを調べる) |
| 範囲の切り分け | 診断(どこが・どこまで悪いのかを見極める) |
| 一時対応 | 応急処置(まず止血する) |
| 恒久対策 | 根本治療・生活指導(再発しないようにする) |
| 報告 | カルテ・診断書の作成(記録として残す) |

応急処置だけして根本治療をしない患者がいたら心配になりますよね。インシデント対応も同じで、一時対応だけで終わらせず、必ず恒久対策まで実施することが重要です。この順番を飛ばしたり入れ替えたりしないことが、対応の品質を左右します。特に「恒久対策」を飛ばして「応急対応」だけで終わらせてしまうミスが最も多いので注意しましょう。

## ポートフォリオへの書き方例

面接やポートフォリオでは、対応の「型」を身につけていることが伝わるように書くと評価されやすくなります。以下は記載例です。

> **セキュリティインシデント対応(不審ログイン調査)**
> Linuxサーバー(Ubuntu Server)へのSSH総当たり攻撃を想定したインシデント対応を実施。`/var/log/auth.log`および`last`/`lastb`コマンドを用いたログ調査により攻撃の事実確認と影響範囲の切り分けを行い、該当アカウントの一時ロックおよびファイアウォールによるIPアドレス遮断で一時対応を実施。再発防止のためfail2banを導入したブルートフォース対策、SSHのパスワード認証廃止・鍵認証への統一、パスワードポリシーの強化(有効期限設定)を行った。対応完了後は発生日時・検知経緯・影響範囲・対応内容・再発防止策をまとめたインシデント報告書を作成し、事実確認から報告までの一連のインシデント対応プロセスを一人称で実践した。
