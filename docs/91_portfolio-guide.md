# ポートフォリオへのまとめ方

この演習パックに取り組んだ成果は、そのままにしておくと「自分の中の経験」で終わってしまいます。採用担当者に伝わる形に整理して初めて、転職活動での武器になります。このドキュメントでは、演習の各テーマ(このドキュメントでは「案件」と呼びます)への取り組みを、GitHub・職務経歴書/履歴書・面接という3つの場面でどう見せるかを具体的に解説します。

## 1. ポートフォリオ全体の考え方

サーバー構築の未経験者採用では、知識量そのものより「わからないことにぶつかったときにどう調べ、どう解決したか」という**プロセス**が評価されます。演習の結果(動いたかどうか)だけでなく、途中経過を丁寧に残すことを意識しましょう。

以下の3点を、案件ごとの最終チェックリストとして使ってください。

- [ ] 各案件のゴールと使った技術要素が一目でわかる
- [ ] つまずいた点と解決方法が記録されている
- [ ] 誰が読んでも再現できる手順になっている

## 2. GitHubリポジトリでの見せ方

GitHubは、ファイルの変更履歴を保存・管理する仕組み(バージョン管理)を使いながらソースコードやドキュメントを公開できるサービスです。ここでの「リポジトリ」とは、案件のファイル一式をひとまとめに管理する保管庫のことを指します。

**リポジトリ構成の例**

この演習パック自体が `cases/case01_pc-setup.md` のように案件ごとにファイルを分ける構成になっています。自分のポートフォリオリポジトリでも、同じように案件(演習の1テーマ)ごとにフォルダを分け、リポジトリ全体のREADME(そのリポジトリの目的や使い方を説明する文書)から各案件へリンクする構成がおすすめです。

```text
portfolio-infra/
├── README.md                        ← 全体の目次・自己紹介
├── case01_pc-setup/
│   ├── README.md                    ← この案件専用のREADME(取り組んだ結果)
│   └── notes.md                     ← 作業ログ
├── case05_linux-server-setup/
│   ├── README.md
│   └── notes.md
└── case06_web-server/
    ├── README.md
    ├── notes.md
    └── screenshots/
```

**全体READMEの構成例**

```markdown
# インフラ構築ポートフォリオ

## 自己紹介
サーバー構築エンジニアを目指して学習中の〇〇です。
「ITサポート基礎演習案件パック」の10案件に、自宅の仮想環境(VirtualBox)で取り組みました。

## 取り組んだ案件一覧
| No | 案件名 | 使用技術 | リンク |
|----|--------|----------|--------|
| case01 | PC初期セットアップ対応 | Windows | [詳細](./case01_pc-setup) |
| case05 | Linuxサーバー初期構築 | Ubuntu Server, SSH | [詳細](./case05_linux-server-setup) |
| case06 | Webサーバー構築 | Nginx, ufw | [詳細](./case06_web-server) |

## 学習環境
VirtualBox上にUbuntu Server / Windows Serverの検証環境を構築し取り組んでいます。
```

各案件フォルダのREADMEには「目的」「構成図(簡単な文字図でも可)」「手順概要」「工夫した点」「参考にした公式ドキュメント」を書くと、実務に近い体裁になります。

**コミットの粒度とメッセージの書き方**

コミット(変更内容を1つの記録として保存する単位)は、**案件を1つ終えるごと**、あるいは**意味のある作業のまとまりごと**に行いましょう。すべてをまとめて1コミットにしてしまうと、取り組みの過程が見えなくなり、せっかくの学習プロセスが伝わりません。

```bash
git add case06_web-server/
git commit -m "Webサーバー構築: Nginxのインストールと初期設定を追加"
```

コミットメッセージの例:

- `add: case06 Nginxの基本設定ファイルを作成`
- `fix: ufwのポート開放漏れによりアクセスできない問題を修正`
- `docs: case05のREADMEにトラブルシューティングを追記`

「add(追加)」「fix(修正)」「docs(ドキュメント)」のように接頭辞をつけると、変更内容が一目でわかり、丁寧に管理している印象を与えられます。実務でも「Conventional Commits」と呼ばれる、接頭辞でコミットの種類を示す命名規則(標準的には feat/fix/docs などを使います)がよく使われています。案件のコミットでは、まず「追加(add)」「修正(fix)」「ドキュメント(docs)」の3種類を使い分けられれば十分です。

> **コツ**: 「動かない」ときは、アプリ自身のログだけでなく、`ufw status`(ファイアウォールで通信が塞がれていないか)もあわせて確認する、と覚えておくと役立ちます。案件06・09・10で繰り返し出てくる切り分けの型です。

## 3. 作業ログ・スクリーンショットの残し方

各案件フォルダに `notes.md` として作業ログを残す習慣をつけましょう。特に**つまずいた点と解決方法**は、面接での会話の材料になる最も価値のある記録です。

> **コツ**: 何を書けばよいか迷ったら「症状→原因→対処→学び」の4点セット(カルテを書くイメージ、と覚えると忘れにくいです)を埋めるだけで十分です。

```markdown
# 作業ログ: Webサーバー構築(案件06)

## 実施日
2026-08-20〜2026-08-22

## つまずいた点(症状)
Nginxを起動したのに、ブラウザからアクセスできなかった。

## 原因と解決方法
ufw(ファイアウォール)で80番ポートを許可していなかった。
`sudo ufw allow 'Nginx HTTP'` を実行したあと、
`sudo ufw status` で許可されたことを確認して解決した。

## 学んだこと
サービスを起動しただけでは通信できず、ファイアウォール設定も
セットで確認する必要があると理解した。
```

エラー画面や設定完了後の動作確認画面はスクリーンショットとして保存し、`screenshots/` フォルダにまとめて `notes.md` からリンクしておくと説得力が増します。個人情報やグローバルIPアドレスが写り込んでいないか、公開前に必ず確認してください。

## 4. 職務経歴書・履歴書への書き方(例文)

独学での取り組みは、正直に書いても十分に評価されます。実務経験と誤解されない書き方を心がけましょう。

**例文1(職務経歴書の自己PR欄向け)**
> 転職に向けた独学の一環として、自宅の仮想環境でWebサーバー・DNSサーバー・監視ツールの構築演習に取り組みました(全〇件、GitHubで公開)。公式ドキュメントを参照しながら構築し、発生したエラーは原因を切り分けて解決する経験を積みました。

**例文2(短くまとめる場合)**
> 独学でのポートフォリオ制作として、Linuxサーバー構築の演習に取り組んでいます。設定手順や、つまずいた点と解決策をGitHubにまとめて公開しています(詳細はGitHubリポジトリをご参照ください)。

**例文3(学習継続の姿勢を強調)**
> 実務経験はありませんが、独学でサーバー構築の基礎を学び、複数の演習課題をポートフォリオとしてGitHubに公開しています。今後はLinuC(Linux技術者認定試験)などの資格取得と並行し、より実践的な構成にも挑戦していきたいと考えています。

いずれも「独学」「演習」「自主学習」という言葉を明記し、実務と誤解されない表現にしている点がポイントです。

## 5. 面接で聞かれやすい質問と回答の組み立て方

回答を組み立てるときは、次の2つのフレームワークを使い分けると迷いません。

- **PREP法**: 結論(Point)→理由(Reason)→具体例(Example)→結論(Point)の順で話す型。意見や動機を聞かれたときに向いています。
- **STAR法**: 状況(Situation)→課題(Task)→行動(Action)→結果(Result)の順で話す型。トラブル対応など、エピソードを聞かれたときに向いています。

| 想定質問 | 回答を組み立てるポイント |
|---|---|
| なぜこの案件に取り組んだのか | PREP法で、志望職種に必要とされる技術要素と選んだ理由を結びつける |
| 一番苦労した案件と乗り越え方 | STAR法で、「発生した事象→調べた方法・原因の切り分け方→解決策」の順に具体的に話す |
| 次に学びたいことは | PREP法で、今回できなかったこと(冗長化、自動化、クラウド化など)を具体的に挙げる |
| 一人で学習を続けられた理由 | 学習のペース管理や情報収集の工夫(公式ドキュメント、コミュニティの活用など)を具体例とともに伝える |

どちらの型も、最後に「そこから何を学んだか」を一言添えると、単なる作業報告ではなく成長のエピソードとして伝わります。

## 6. 誠実さに関する注意

ポートフォリオで最も大切なのは、正直であることです。

- [ ] 「実務経験」ではなく「自主学習」「独学」「演習」という言葉を一貫して使う
- [ ] チームでの共同開発をしたかのような表現(「〇〇を担当しました」等)は使わない
- [ ] 参考にした教材・書籍・公式ドキュメントがある場合は隠さず伝える
- [ ] わからなかったこと・完璧にできなかったことも正直に話す

未経験者採用では、経験の量よりも「学ぶ姿勢」と「誠実さ」が重視されます。背伸びした表現で採用されても、入社後のギャップに苦しむのは自分自身です。今回の演習で得た確かな学びを、そのままの言葉で伝えることが、結果的に一番の近道になります。
